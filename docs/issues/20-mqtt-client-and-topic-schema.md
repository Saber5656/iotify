# Implement the MQTT client, topic schema, and state publishing

## Summary
Implement `iotify.integrations.mqtt`: aiomqtt-based client with LWT availability, reconnect backoff, TLS/auth support, the DESIGN §8.1 topic schema, and bus-driven publishing of sensor states/availability and camera status.

## Context
MQTT is the primary integration output (owner decision) and the transport for HA discovery (issue 21). Reliability semantics (retained states, LWT) determine how trustworthy iotify looks inside Home Assistant.

## Scope
- `src/iotify/integrations/mqtt/topics.py`: pure topic-string builders (all §8.1 topics; base topic configurable).
- `src/iotify/integrations/mqtt/client.py`: `MqttPublisher` — `start(config, secrets, bus)`, `stop()`, connection state property (for `/system/info`), publish helpers with QoS/retain per §8.1.
- `aiomqtt` runtime dep (rationale; K4 notes paho fallback).

## Detailed Requirements
1. Connection: client id `iotify-<hostid>` where hostid = first 8 hex of sha256(machine hostname + data-dir path) (stable across restarts, no PII); username from config, password from secrets; TLS when `mqtt.tls.enabled` (CA path, optional client cert/key); connect timeout 10 s.
2. LWT: topic `iotify/bridge/status`, payload `offline`, retained, QoS 1; on connect publish `online` retained; on graceful stop publish `offline` retained then disconnect.
3. Reconnect: loop with exponential backoff 1→60 s ±20 % jitter; while disconnected, publishes are queued in a bounded deque (maxlen 1000, drop-oldest, warn once per overflow episode); queue flushed on reconnect (retained states make drops harmless).
4. Bus subscriptions → publishes:
   - `sensor.reading_persisted` (emitted by the pipeline for every persisted reading incl. heartbeats — DESIGN §6.5, issue 15) → `iotify/sensor/<id>/state` retained QoS 1, payload = §6.2 value + `{"confidence":…,"ts":…}`;
   - `sensor.availability` → `iotify/sensor/<id>/availability` retained `online|offline`;
   - `camera.health_changed` → `iotify/camera/<id>/status` retained JSON.
5. Topic ids are §7.3 slugs by construction — assert (defense in depth) and refuse to publish otherwise.
6. Sensor deletion (bus `sensor.deleted`, emitted by the CRUD API — DESIGN §6.5, issue 17-12) → publish empty retained payloads to that sensor's state/availability topics (clears broker retention).
7. `mqtt.enabled: false` → module never constructs a client; `/system/info` shows `"disabled"`.
8. No subscriptions to inbound command topics in v1 (control flows via HA services, ADR-002) — document explicitly.
9. Integration tests run against the CI Mosquitto service (issue 05) and a local `mosquitto` via docker for dev (`make mqtt-dev` target).

## Acceptance Criteria
- [ ] Connect/publish/LWT verified against real Mosquitto: kill -9 the hub → broker delivers retained `offline` (LWT) to a test subscriber.
- [ ] Sensor state change lands on the right topic, retained, correct JSON (subscriber asserts).
- [ ] Broker restart mid-run: hub reconnects with backoff, re-publishes `online`, flushes queued states (test restarts the container).
- [ ] TLS config path validated at startup (bad CA path → startup error naming the path); TLS connect exercised against Mosquitto with test certs (checked-in, obviously-test-only, generated by a committed script).
- [ ] Deleting a sensor clears its retained topics.
- [ ] Password absent from logs (redaction test).

## Validation
`pytest tests/integration/test_mqtt.py` (Mosquitto service container; docker restart scenario marked `slow`).

## Dependencies
02, 03, 09 (bus), 15 (reading events), 05 (CI broker).

## Non-goals
No HA discovery payloads (21), no inbound MQTT commands, no MQTT v5-only features, no bridging multiple brokers.
